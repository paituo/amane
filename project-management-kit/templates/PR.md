# PR 契约

本文规定 PR 的正文结构、CI 节奏、Issue 关联与合入方式. 可作为 `docs/dev/pr.md` 使用, 也可直接放进
`skills/pr/SKILL.md`.

## 工作区

PR 默认使用**独立 worktree**, 不在主检出开发, 除非用户明确要求.

```bash
git worktree add ../<repo>-<topic> -b <type>/<topic> <BRANCH>
```

分支名用 `<type>/<topic>`: `fix/`、`feat/`、`docs/`、`refactor/`. 收尾时删除 worktree 与本地分支.

## 正文

顺序固定: **Summary → 接口与数据变更 → Implementation → Test plan → Close/Fix 或 Related**.

### Summary

无序列表, 写本 PR 对外交付的能力或解决的缺陷. 每条为**无标点单句**, 简明扼要.

禁止:

- 源码标识符 (字段、类、函数、API 参数);
- 对调用链 / 控制流 / 状态转移的纯粹描述;
- 实现细节 (边界条件、约束等).

这些内容如对审查有帮助, 写入 Implementation.

### 接口与数据变更

表格, 三列: 类别 | 变更 | 说明.

逐类只列实际改动的面:

- OpenAPI 端点 (新增 / 删除, 给出方法与路径, 写明个数);
- 任务类型与任务模型;
- 请求 / 响应字段;
- 数据库模型 (表 / 枚举 / 字段语义);
- 数据库迁移 (revision 与影响).

未改动的面不写. 大规模 PR 必写; 小 PR (如内部 bug 修复) 可省略整节.

### Implementation

无序列表, 写实现方案与契约, 可省略. 格式要求:

- 开头先给一句整体形状 (谁产出、谁确认、谁执行), 让读者拿到心智模型再看细节;
- 每条一个要点, 用粗体小标题领起 (`- **存放**: …`);
- 单条控制在**一行左右**: 条件、原因与例外并入同一条, 禁止堆进括号绕成长句;
- 条目按读者的理解顺序排列 (产出 → 存放 → 执行 → 边界 → 读取 → 兼容 → 命名), 不按代码结构.

### Test plan

check-list, 逐项写明验证方式与结果.

### Issue 关联

写在正文**末尾**:

- **彻底解决** (PR 就是在修这个 bug / 做这个 feature): 用 `Close` / `Fix`, 合并时自动关闭;
- **只是关联、并未彻底解决**: 单独一节 `Related` 列出. 已被 `Close` / `Fix` 的不必重复.

```markdown
## Related

- #56
- #78

Close #12
Fix #34
```

### 禁止中间态

正文只描述最终实现. 开发过程中的增强、修复、重命名与返工一律不写入, 也不作为验收项列出.
两类例外必须写: 相对 base 分支的行为改变, 以及范围声明 (未实现项、只写 `Related` 的原因).

### 迁移警告

PR 含数据库 schema 变更 / 新 migration 时, **正文最前面**固定放:

```markdown
> ❗ **此 PR 包含 DB migration**
```

## 正文示例

```markdown
> ❗ **此 PR 包含 DB migration**

## Summary

- 支持按演员筛选作品列表
- 修复筛选条件在翻页后丢失

## 接口与数据变更

| 类别 | 变更 | 说明 |
|------|------|------|
| OpenAPI | 新增 `GET /actors` 的 `gender` 查询参数 | 可选, 枚举值 male / female |
| 数据库 | `actor` 表新增 `gender` 字段 | 默认空, 不影响既有数据 |
| 迁移 | `a1b2c3d4e5f6` | 新增字段, 无回填 |

## Implementation

整体形状: 前端只传筛选条件, 后端负责校验并拼查询, 数据库按索引返回.

- **参数校验**: 非法枚举返回 422, 不静默忽略
- **查询**: 筛选与分页共用同一条件对象, 避免翻页时丢失
- **兼容**: 缺省不筛选, 保持旧行为

## Test plan

- [x] `GET /actors?gender=male` 只返回匹配项
- [x] 非法值返回 422, 错误信息包含字段名
- [x] 翻页后筛选条件保持

## Related

- #56

Close #42
```

## CI

**推送时机**: 不要每提交一次就推一次. 本地先把改动做完, 由用户确认功能或修复已完整实现后再推.
一轮 CI 通常要几分钟, 逐次推送会把同一套检查反复跑.

推送时按逻辑变更压缩本地提交 (squash), 保留可分节的粒度, 不要把十几次微调原样推上去.

推送后必须跟踪这一轮 CI, 失败则修复:

- 只需要改测试代码时可直接操作; 要改业务代码时先报告用户并获得许可;
- 修复需要改动本 PR 的设计方案时, 必须向用户报告;
- 修完按同样节奏攒着, 等用户确认后再推.

PR 的 CI 通过之后再合入. 合入后 main 上的那一轮 CI 不必等待 —— 那是同一棵树的重复运行.
rebase / force-push 会作废上一轮, 这类改动必须重新等这一轮通过.

## 合入

- 首选 **squash**;
- 非常简单的 PR 可用 **rebase**;
- **永远不要用 merge commit** 把 PR 合进主分支;
- 合并使用 PR 自身的标题, 不在合并时另指定 message; 要改合并提交内容就改 PR 标题;
- 合入后删除该 PR 的 worktree 与本地分支; 若从本仓库分支创建, 还要删除远程分支.

## 堆叠式 PR

一个需求涉及多个领域、预期规模较大时, 用堆叠式 PR: 改动按依赖分成多层, 上层 PR 的目标分支是下层分支.

- 用 `gh stack init` / `add` 维护; `submit` 创建 Stack 对象;
- CI 依据 Stack 对象决定 base, 不要只手工 `gh pr edit --base`;
- 堆叠内不能逐个合并, 用 `gh stack merge --yes --squash` 原子合入;
- 自下而上合入, 下层合入后把上层剩余提交重基到新主分支;
- 重新核对生成物与数据库迁移.

## 数据库迁移的并行 PR

多个并行 PR 各自基于主分支最后一个 revision, 直接合入会让迁移图分叉 (multiple heads).
合并这类 PR 之前:

1. 把 `origin/<BRANCH>` merge 或 rebase 进该 PR 分支;
2. `alembic heads` — 必须只剩一个 head;
3. 若多个 head: 不要 `alembic merge`; 把本 PR 里最早那条 revision 的 `down_revision` 改成当前主分支的
   head, 排成一条链; 禁止手写新的 revision ID;
4. 推上去, 再等 CI, 再 squash.

连续合多个带 migration 的 PR 时, 每合一个都要重新执行 1–3.
