# AI 使用政策

本文件规定 AI 在 Issue、Pull Request、评论与代码贡献中的使用方式。
替换 `<PROJECT>` 与仓库地址后即可使用。

## 0. 基本原则

本项目允许并鼓励合理使用 AI 工具. AI 可以提高效率, 但不会因此免除贡献者的责任.
无论内容由人类还是 AI 生成, 最终提交内容都必须符合本项目的质量要求, 并由提交者对其负责.

本政策主要适用于外部贡献. 由仓库 Owner、Maintainer 或其他具有相应权限的人员发起的 Issue 和 PR
不受本政策的强制约束, 但仍建议遵循其中的最佳实践.

## 1. Issue

Issue 须经 `.github/ISSUE_TEMPLATE/` 的模板创建; **禁止经 GitHub CLI 或 REST API 创建无模板的 Issue**.
经 CLI 或 REST API 提交时, 正文必须与所用模板的字段一致.

允许使用 AI 创建、撰写、翻译、整理、润色和修改 Issue, 包括问题描述、复现步骤、功能请求、环境信息整理、
错误日志分析和总结. 但是, AI 生成的 Issue 必须经过提交者本人 review, 并确保:

- 准确描述实际遇到的问题或实际需求;
- 不包含未经验证的 AI 推测, 必要时明确标注不确定内容;
- 语言自然、清晰、易于人类阅读;
- 具有足够上下文, 使其他贡献者能够理解问题;
- 不存在明显的 AI 生成痕迹导致的冗余、重复或晦涩表达.

使用 AI 时必须在 Issue 中披露, 程度分三级:

| 级别 | 含义 |
|------|------|
| AI 部分撰写或润色 | AI 仅参与部分内容的生成、整理或语言润色, 主要内容由人类提供 |
| 主要由 AI 撰写 | 正文主要由 AI 生成, 人类进行了 review、修改和确认 |
| AI 自动化创建 | 主要由自动化 AI Agent 或其他自动化流程创建, 人类未逐项撰写 |

可以进一步说明使用的模型及 Agent 工具, 但不是强制要求.

**AI 的代码分析能力与文本表达能力并不一定匹配.** 即使前沿模型能较好地分析代码问题, 其起草的文本仍可能
冗长、拗口、机械化或缺乏重点. 因此提交者不能直接把 AI 输出作为 Issue 提交, 必须人工 review 和必要的修改.

## 2. Pull Request

### 2.1 代码变更

允许在开发过程中使用 AI, 包括方案设计、编写代码 / 注释 / 测试 / 文档、调试及 review, 但必须遵循:

- **所有提交到本项目的代码变更都必须经过人工 review**;
- **PR 作者必须对代码变更具有完整深入的理解, 并对设计动机、方案取舍、破坏性变更进行完整评估与披露**;
- **不应提交自己无法理解的 AI 生成代码**.

如果**在 PR 上投入的人力 (例如编写 prompt) 少于 review 它所需的人力**, 则不要提交 PR.
这种情况下, 维护者自行完成通常比审查外部 PR 更快、更安全.

### 2.2 PR description

允许使用 AI 撰写或润色 title、description、summary、test plan, 但所有文本必须经过提交者本人 review.
提交者应确保 PR description:

- 准确描述实际的代码变更;
- 清晰说明变更的目的和背景;
- 准确描述测试情况;
- 不包含未经验证的 AI 推测;
- 语言自然、清晰、易于人类阅读;
- 避免冗余、机械化和难以阅读的 AI 风格表达.

### 2.3 披露

PR 使用 AI 时必须披露, 程度分三级:

| 级别 | 含义 |
|------|------|
| AI 部分撰写或润色 | AI 仅参与部分代码、文档、测试或 PR 文本的生成、整理或润色 |
| 主要由 AI 撰写 | 主要代码或其他主要内容由 AI 生成, 作者进行了人工 review、修改和验证 |
| AI 自动化创建 | 主要由 AI Agent 或其他自动化流程完成, 作者仅负责提出任务、review 和最终提交 |

后两级可进一步说明使用的模型及 Agent 工具.

## 3. 滥用

允许使用 AI, 不意味着可以把项目维护者当作 AI 输出的人工验证服务.
维护者需要投入实际人力阅读、理解、测试和处理 Issue、PR 与评论. 一次 prompt 生成、却要求维护者投入大量
时间分析、清理、验证和解释的内容, 会给维护工作造成不合理负担.

因此:

- 不要直接复制粘贴未经 review 的 LLM 输出;
- 不要使用 AI 大量生成低质量、重复或无实际价值的 Issue、PR 或评论;
- 不要提交自己无法理解或解释的 AI 生成代码;
- 不要通过自动化工具持续创建需要维护者逐一处理的低质量 PR 或 Issue;
- 不要利用 AI 批量生成评论、建议或其他内容来干扰正常维护.

### 3.1 疑似 AI 生成内容

如果 Issue、PR 或评论表现出明显的自动化或低质量特征, 维护者可以要求作者解释、修改或重新提交.
无法提供合理人工解释, 或内容明显属于未经人工处理的自动化生成结果时, 维护者可以直接关闭对应的
Issue 或 PR.

### 3.2 Spam 与滥用

持续自动化提交低质量内容, 使维护者不得不投入大量人工时间筛选和处理, 属于对维护人力的滥用.
维护者可采取包括但不限于以下措施:

- 关闭相关 Issue 或 PR;
- 删除明显的 spam 内容;
- 限制相关 Issue 或 PR 的进一步参与;
- 将相关账号加入 block list;
- 对重复提交或持续滥用的账号进行封禁;
- 在必要时采取平台提供的其他管理措施.

## 4. 目标

1. **Human accountability**: 提交者必须对最终内容负责.
2. **Human review**: AI 生成的内容必须经过适当程度的人工 review.
3. **Human understanding**: 提交代码的作者必须真正理解自己提交的代码, 而不是将 AI 视为开发主体.
4. **Transparency**: 外部贡献中的 AI 使用应当披露, 使维护者了解贡献的大致来源.
5. **Readability**: Issue 和 PR 的文字以人类读者为主要对象, 清晰、自然、直接.
6. **Respect for maintainer effort**: 贡献者不应通过低质量或过度自动化的内容, 把不合理的审查与维护成本
   转嫁给维护者.
